# AI Summary

Summaries are generated by a **remote** OpenAI-compatible chat model. Local
GGUF/llama.cpp inference was explicitly deferred; see ROADMAP.

## Contract

Input: a media row plus a non-empty transcript. Output: a summary row containing
five structured fields and a rendered Markdown document.

All content is derived from the real transcript. There is no canned output: if
the model call fails, `Generate` returns the error, sets
`media.summary_status = 'error'`, and stores nothing.

## Configuration

Stored in `settings` under `llm_base_url`, `llm_api_key`, `llm_model`.

Defaults: `https://api.deepseek.com/v1`, model `deepseek-chat`.

`BaseURL` is normalized to end with `/v1`. If no API key is set and the host is
not `localhost`/`127.0.0.1`, `GenerateSummary` fails immediately with:

> API Key not configured. Please click ⚙ Config to configure your AI API Key

## Prompt and parsing

The transcript is flattened to `[MM:SS] text` lines and sent with a system
prompt demanding strict JSON with these keys:

```json
{
  "overview": "string",
  "key_points": ["string"],
  "action_items": ["string"],
  "chapters": [{ "start_ms": 0, "title": "string", "summary": "string" }],
  "highlights": [{ "start_ms": 0, "note": "string" }]
}
```

The reply is stripped of Markdown fences before `json.Unmarshal`. If the model
returns prose instead of JSON, the raw text is kept as `overview` rather than
discarded — the user still sees something true to the transcript, and the
Markdown export still works.

## Storage

`summary` is one row per media (`UNIQUE(media_id)`):

| Column | Content |
|---|---|
| `overview` | plain-text overview |
| `key_points_json` | `[]string` as JSON |
| `action_items_json` | `[]string` as JSON |
| `chapters_json` | `[]Chapter` as JSON |
| `highlights_json` | `[]Highlight` as JSON |
| `content_markdown` | full rendered document |
| `model`, `created_at` | provenance |

Storing both the structured JSON and the Markdown means the UI can render rich
sections and timestamps while export stays a single string write.

## Markdown rendering

`FormatMarkdown` emits:

```
# <title> — AI Summary
## Overview
## Key Points        (- bullet)
## Action Items      (- [ ] checkbox)
## Chapters          (- **[MM:SS] Title**: summary)
## Highlights        (- **[MM:SS]**: note)
```

Empty sections are omitted entirely.

## UI behavior

Summary tab:

- transcript missing → "Transcript Required" with a button to the Transcript tab
- `summary_status = pending` → spinner
- no summary → "Generate"
- summary present → Overview / Key Points / Action Items / Chapters / Highlights,
  with chapters and highlights clickable to jump the player
- **Copy** copies `contentMarkdown` via `navigator.clipboard`
- **Export** writes `contentMarkdown` to a `.md` file chosen in a native dialog
- **⚙ Config** edits base URL / API key / model inline

## Timeouts

90 s per request, single shot — the entire transcript goes into one prompt. Very
long transcripts can exceed model context limits; chunked map-reduce
summarization is not implemented (ROADMAP).

## Testing

- `TestFormatMarkdown` — every section, `- [ ]` items, `[01:00]` time formatting.
- `TestGenerateSummaryWithServer` — local `httptest` server asserts the request
  carries `Authorization: Bearer`, returns structured JSON, and that all five
  fields plus Markdown are populated correctly.
- `TestGenerateSummaryRequiresAPIKey` — fails with the documented message.
- `TestSettingsPersist` — settings round-trip.
- `TestSummaryLifecycle` — end-to-end: media + transcript → `Generate` →
  `summary_status = done` → re-read row → verify every field.

These use a local HTTP server only to avoid depending on a paid API in CI; the
HTTP client code path is the production one.
